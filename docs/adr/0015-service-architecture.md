# 0015. 省庁向けエディタはサービスとして提供する。証明はブラウザで走る検証済み関数、サーバーはデータ・保存・協調編集のみ

状態: accepted（2026-09-20）

## 文脈

[ADR-0014](0014-proofs-at-build-time-editor-runs-verified-code.md) は「証明は開発時に一度、エディタは検証済み関数を実行する」と決めた。
しかし [ADR-0011](0011-lean-as-reference-for-consolidation.md) の「実データを Lean に出力して `consolidates` を `native_decide` で検査する」
という記述が、リポジトリと CI を前提にした書き方になっており、**製品の経路**と**開発時の検証**が混ざって読める（2026-09-20 の議論）。

想定する提供形態は、省庁の担当者が改め文（構造化記述、[ADR-0012](0012-structured-authoring.md)）を書き、
入力のたびに「溶け込むか」「発射台は合っているか」「施行順序に依存しないか」「他の改正と衝突しないか」「ハネの手当てが要るか」が
**その場で**返るエディタである。担当者はリポジトリに何かを入れないし、CI を待たない。Lean の存在も知らなくてよい。

## 判断

1. **利用者に見える「証明」は、証明済み関数の実行結果である。** 担当者が知りたいことは全部、`applyUnit` / `independent` / `dependsOn` /
   `scheduleOk` / `hasConflict` / ハネ候補の生成といった**関数の値**である。「どんな入力にも成り立つ」部分（`applyUnit_comm` 等）は
   開発時に一度証明してあり、実行時に証明し直すものは無い
2. **Lean が走るのはサービスを作る側のビルドだけ。** `lake build` でメタ定理を検証し、同じ Lean ソースから C 経由で WASM を生成する。
   担当者の手元にもサービスのサーバーにも、Lean のカーネルやエラボレータは置かない
3. **ブラウザが WASM を実行する。** キー入力ごとに結果を返す。各判定には「どの定理に裏付けられているか」（定理名）を添えて表示する
   （[TODO](../TODO.md) の「証明結果に Provenance を引きずる」）
4. **サーバーの役割は証明ではない。** 置く理由は次の 3 つに限る
   - 法令データ: e-Gov のリビジョン、他法令への波及（[09](../09-cross-law-impact.md)）に要る法令空間。ブラウザに全部は載らない
   - 保存と履歴: 下書き、発射台の指定、施行シナリオ
   - 協調編集: 複数の担当者が同じ改正案を同時に編集する場合のエディタ層（[ADR-0013](0013-identity-patches.md) §6。ここだけ CRDT）
5. **証跡（審査資料に添える記録）は決定性で作る。** `applyUnit` は決定的なので、
   `(発射台リビジョンのハッシュ, 改正単位, 結果のハッシュ, WASM のバージョン)` を出せば、第三者は同じ関数を走らせて再現できる。
   `native_decide` の定理も根拠は「コンパイル済み関数が true を返した」（公理 `Lean.ofReduceBool`）なので、これと同じ強さである。
   それ以上の強さ（`decide` で閉じる、独立カーネルで再検査する）は開発成果物である WASM と定理に対して一度行えばよく、改正案ごとには行わない
6. **[ADR-0011](0011-lean-as-reference-for-consolidation.md) の `consolidates` 定理は開発時の回帰テストと位置づけ直す。**
   Lean の `applyUnit` が e-Gov の過去の改正を再現することを確かめるもので、モデルが現実に合っている裏付けである。
   担当者の改正案ごとに作るものではなく、サービスの機能でもない
7. **入力ごとに走る探索は Z3 で、これは証明ではない。** 改正後の法律の性質（期間・金額・矛盾、[07](../07-verification.md)）を担当者が問う場合は
   Z3 の反例探索で、小さい問題はブラウザ（Z3 の WASM ビルド）、大きければサーバー。Lean とは別の層

## 理由

- 証明の対象はプログラムであってデータである改正案ではない。一度証明した性質はどの入力にも自動で及ぶ（ADR-0014）
- 「リアルタイムに証明する」という要求は「検証済みデシジョンプロシージャを実行時に走らせる」で満たせる。reflection / `native_decide` と同じ定石
- 開発時の検証と製品の経路を分けないと、「CI が要る」「サーバーで Lean を動かす」という誤った要件が生える

## 結果（トレードオフ）

- 何がどこで動くか:

  | 層 | 動くもの | Lean |
  |---|---|---|
  | 開発側のビルド | `lake build`（メタ定理の検証、`consolidates` 回帰テスト）、Lean → C → WASM | 走る |
  | ブラウザ | WASM の `applyUnit` と検査関数、改め文と新旧対照表の描画、証跡の生成 | 走らない |
  | サービスのサーバー | 法令データ、保存・履歴、協調編集 | 走らない |

- WASM は Lean の C 出力から作る（ADR-0014 §5 の第 1 の経路）。Rust `lawean-amend` からの wasm32 を採ると Lean との一致テストが本線になる
- 証跡の形式（ハッシュの対象、正規化、WASM のバージョン識別）を決める必要がある
- 利用者に出せる保証は「証明済みの関数が、この入力に対してこう答えた」まで。「この改正案について新しい定理を証明した」形の文言は使わない
- 法令空間をサーバーに置くので、他法令への波及の検査だけはサーバー往復が要る。自法令内の検査はブラウザで閉じる
