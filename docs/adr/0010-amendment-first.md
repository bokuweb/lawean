# 0010. 主役は改正。patch 代数を Lean で定義し、Z3 は反例オラクルに置く

状態: accepted（2026-09-20）

## 文脈

法制執務の実態（[08-amendment.md](../08-amendment.md) §1）:

- 成立する法律の約 8 割は一部改正法（令和7年通常国会: 成立 75 本のうち新規の法律は 14 本）。改め文（溶け込み方式）で書かれる
- 改め文が機械的に溶け込まない事例が法律・政令で毎年 2〜3.7%。原因は施行日の書き分け、溶け込み順（他法令が先に改正して対象が無い）、調整規定、官報正誤、表記の不一致
- 内閣法制局・各府省の審査は目視。ハネ改正（項の挿入で「前項」がずれる等）は e-LAWS が自法令内の相対参照を出せないため人が探している
- デジタル庁のエディタ検証（2024）は「改正単位 / 改正シナリオ / 法令リビジョン」というデータ構造に到達したが、複数の施行順序ごとの溶け込み後条文の自動生成は「技術的にハードルが高い」として優先度を下げた

ここまでの lawean は「1 バージョンの法令を IR にして検証する」だった。ユースケースを「改正法が正しいか」「適用後のある時点で矛盾がないか」に置き直す。

## 判断

1. **v0.2 の主役は改正。** 改め文 → 改正単位（patch）→ 施行シナリオごとのリビジョン → 検査、を本線にする
2. **patch 代数は Lean 4 で定義し、実行もする。** `apply : Revision → AmendUnit → Option Revision`（対象が無ければ失敗）と参照索引の更新を Lean で書き、Rust（XML・参照解決）から呼ぶ。意味論を二重に持たない
3. **Lean で証明するのはメタ定理。** 個々の改正の検査は `decide` で済むが、価値は「全ての法令・全ての改正について成り立つこと」: 改正単位の可換性の十分条件（触る規定が交わらず条番号を動かさない）、条・項の挿入が後続の相対参照をハネさせること、など。これで施行順序パターンの列挙を圧縮する
4. **Z3 は反例オラクルとして残す。** 溶け込み後リビジョンの性質（期間・金額・矛盾）は Lean でも `omega` / `decide` で閉じるが、成り立たないときの反例は Z3 が出す。書いている途中の改正法に「この施行順だと第二条が消える」と返す用途
5. 既存法令の取り込み（層 1・層 2）はそのまま。改正の検査は Source IR（構造と参照）だけで大半が成立し、Semantic IR は (b) の矛盾検査で使う

## 理由

- 実務の 8 割が改正であり、審査の負担と誤りの原因がそこに集中している
- 改め文の語彙は閉じている（改める / 加える / 削る / 〜とし / 繰り下げる / 次のように改める）。パーサは規則で書ける
- 「発射台が違う」「溶け込み順で対象が消える」は patch の部分性と順序依存そのもので、代数として扱うと検査が機械的になる
- e-Gov に改正前後の版が残っている（借地借家法は 2017 年以降 9 版、令和4年法律第48号は 3 段施行）ので、apply の正しさを実データで検証できる

## 結果

- 新 crate `lawean-amend`（改め文パーサ、Source IR への apply、発射台・ハネ・シナリオ検査）と `lean/`（patch 代数とメタ定理）
- 改正法本文は e-Gov の law_data に無い（溶け込み後しか無い）。衆議院の法律本文 HTML から取る。`fixtures/amendments/`
- ADR-0007 の `version_id` はそのまま e-Gov の `law_revision_id`。改正シナリオは version_id の列として表す
- Verification IR（07）は「リビジョンに対する検査」として位置づけ直す
